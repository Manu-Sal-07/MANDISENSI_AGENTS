# Tool and method choices, against the alternatives

Each choice below says what was used, what else was considered, and why. Where the reason is a measurement made in this project, the
source is named; where it is a judgement about engineering fit, it is marked **(judgement)** so the two are not confused.

## Modelling

| Decision | Used | Alternatives considered | Why |
|---|---|---|---|
| Served price forecaster | One pooled gradient-boosted model (XGBoost) per horizon, on log-returns, 51 causal features | A linear model; a 50/50 blend of the two; per-series models; a zero-shot foundation model (Chronos-Bolt); LightGBM; neural networks | The linear blend did not beat the single model on held-out folds (`blend_beats_single: false` in `models/farmer/forecast_models/metadata.json`). Chronos-Bolt had skill −9.4% (1 day) and −2.1% (7 days) against a random walk (`research/docs/RESULTS.md` §1). A plain LightGBM on the same labels was statistically indistinguishable from every neural variant (RESULTS §2), so the learner family is not where the gain is and the simplest fast one was kept. A pooled model with a crop code shares strength across thin series. |
| Prediction target | The h-day log-return `log(p[t+h]/p[t])` | The price level | The naive forecast is exactly zero, so any skill reported is skill the model has; a level model can post a flattering error by echoing yesterday (`forecasting/train.py` docstring). |
| What the decision model learns from | The farmer's **realised** net revenue, including the cost of a trip to a mandi that turned out to be silent | Observed prices only (predict-then-optimise) | Realised labels cut regret by Rs 123 per quintal (95% CI −165 to −87, Holm p < 1e-4) on the same network, and Rs 140 per quintal with LightGBM (RESULTS §2). This is the project's main measured gain. |
| Decision-focused loss | Squared error on realised labels | SPO+ loss; a reporting-probability head; tuning on decision regret | None of the three beat the plain loss: SPO+ vs MSE −25 Rs/q (CI −53 to +3, p = 0.51); the reporting head was worse (+23, p = 0.012); regret tuning −8 (p = 1.00). They are kept in `research/` and reported as negative results, not shipped. |
| Revenue guarantee | Adaptive conformal inference with delayed feedback | A Gaussian floor from residual spread; quantile regression | A naive Gaussian floor on a standard model violated its stated level 27–35% of the time against a 10% target; the adaptive floor violated 4.6 / 10.6 / 23.3% at targets of 5 / 10 / 20% (RESULTS §4). |
| Seasonal/trend decomposition (STL, VMD) before forecasting | Not used | The literature's decompose-then-forecast recipe | Under the published protocol the hybrids show +17 to +70% skill; when the decomposition may not see the future the skill is −15 to 0%, a gap of 30–72 points (RESULTS §1). The method is evaluated in `research/gfmc/leakage.py` and rejected. |
| Specialist-agent ensemble | Four feature-family agents fused by non-negative weights learned inside each fold, summing to at most 1 | Hand-set weights (the earlier design); unconstrained least squares; one model | Unconstrained weights summed to 2.4–3.1 and amplified noise (skill −1.6 to −2.1%); constrained weights are indistinguishable from the single model (`docs/AGENT_COUNCIL.md`). The council is therefore evaluated, shown, and **not** promoted. |
| Hyperparameter search | Optuna (TPE sampler), two inner validation blocks per outer fold, 20 trials for neural and 25 for gradient-boosted models, the same budget for every method | Grid search; fixed defaults | Nesting keeps the outer test blocks unseen by tuning, and an equal budget keeps the comparison fair. Search spaces are in `research/gfmc/specs.py` and the protocol in `research/docs/METHODOLOGY.md`; the finding that tuning on decision regret does not beat tuning on forecast loss is in RESULTS §2. |
| Multiplicity and dependence | Holm correction; day-block and week-block bootstraps; Diebold–Mariano; Model Confidence Set | Uncorrected p-values; i.i.d. bootstrap | Daily decisions and weekly price changes are autocorrelated, and dozens of comparisons are made; uncorrected or i.i.d. intervals would overstate certainty. |

## Application stack

| Decision | Used | Alternatives | Why |
|---|---|---|---|
| API framework | FastAPI | Flask, Django REST | **(judgement)** Async handlers and WebSockets (used by the visualiser and streaming), Pydantic request validation, and an OpenAPI page for free at `/docs`. |
| Front end | Next.js (App Router) + React + Tailwind + TanStack Query | A single-page Vite app; server-rendered templates | **(judgement)** File-based routes for ~30 pages, request caching and de-duplication from TanStack Query, and utility CSS that keeps two visual surfaces (farmer, trader) consistent. Copy is held in per-feature English/Kannada/Hindi tables. |
| Tabular storage | Parquet for panels, JSON for small artefacts, joblib for models | CSV; a database | **(judgement)** Typed, compressed, columnar reads for the multi-year panels; JSON where a person should be able to read an artefact. Postgres and Redis are supported but optional: the application runs without them and the health check reports them as degraded rather than failing. |
| Language model | Hosted open-weight models through Groq (writer `openai/gpt-oss-120b`, judge `qwen/qwen3.8-27b`), behind a provider interface that can also use Anthropic or an OpenAI-compatible endpoint | A single closed model; a local model | The writer and judge are different model families on purpose, so the judge is not marking its own work. The design does not depend on the vendor: every number, name and date is inserted by code and a rule-based path is always available. Measured median latency 6.7 s per explanation and a free-tier limit of 8,000 tokens per minute (`docs/LLM_EVALUATION.md`), which is why responses are cached and rate limits are waited out. |
| Explanation safety | The model paraphrases code-written sentences; a validator and an independent judge gate each sentence | Free generation with a post-hoc number check | A first design let the model choose placeholders and produced correct numbers attached to wrong meanings, which a number check cannot detect. Removing the model's say over meaning fixed it; this is recorded in `docs/LLM_EVALUATION.md`. |
| Tests | pytest (≈640 application tests plus the research suite); a headless-Chrome smoke test of every page (`scripts/smoke_ui.py`); `tsc` and ESLint | Browser-automation frameworks | **(judgement)** The smoke test needs only an installed Chrome, so it runs on any developer machine and in CI without downloading a browser driver. |
| Packaging and deployment | `pyproject.toml`, a Dockerfile, `docker-compose.yml`, `render.yaml`; GitHub Actions for CI | Poetry, conda | **(judgement)** Plain `pyproject.toml` installs with pip anywhere; `requirements.lock` pins the environment the tests were run in. The Docker and Render files are provided; a live deployment has not been verified in this document. |
| Orchestration | One Python script, `scripts/pipeline.py`, with stage dependencies, timing and a JSON report | Make, Airflow, Prefect | **(judgement)** The default pipeline is nine stages on one machine; a script that works on Windows and Linux and has no scheduler to install is enough. A nightly job (`scripts/run_nightly_job.py`) covers the scheduled part. |
